# Tools

Build-time tools that turn an ELF into Lean data, into an Lprog program (layer 0.5) or into a
Pancake program (layer 1). They are layer -1 of the [roadmap](../ROADMAP.md) and are
**untrusted**: whatever they emit as Lean is re-checked by the kernel, and nothing in
`MachineChecked/` imports them. The modules `decompile --to lean` writes (in `Examples/`)
import `Tools.KernelEq` and `Tools.ElfWords`, for `kernel_eq` and the check of their words
against the ELF.

| file | command | what it does |
| --- | --- | --- |
| `GenImage.lean` | `lake exe gen-image ELF NM OUTDIR MODPREFIX [STACKTOP]` | Writes the ELF as Lean data: one module per function (its words and their decoding), the data chunks and the layout. |
| `Infer.lean` | `lake exe infer-contracts ELF NM OUT.tsv STACKTOP PROTLO PROTHI [LEANDIR MODPREFIX IMGPREFIX LAYOUT [REGISTRY [CFI [STATICS]]]]` | For every function, bottom-up over the call graph, infers an interface (`Check.Iface`) and a certificate; with `LEANDIR`, emits them as Lean for the checker to re-check. |
| `FrameSweep.lean` | `lake exe frame-sweep ELF NM OUT.tsv` | Runs the frame analysis on every function and reports which annotations check, and why the others do not. |
| `Decompile.lean` | `lake exe decompile …` | The decompiler. See [below](#decompile). |
| `ToLean.lean` | library; command `check_elf_input` | Implements `decompile --to lean`: the modules it writes, and the check of the other routes' input against the ELF. |
| `KernelEq.lean`, `ElfWords.lean` | library; commands `kernel_eq`, `check_elf_words` | What the modules `--to lean --proved` writes use of the tool: `kernel_eq` and the lemmas a function's theorem is built from its parts with; the functions the `--proved` lift takes, their words, and the check of the words against the ELF. They import `Lean.Elab.Command`, the lift and the ELF reader, not all of `Lean`, so that a written module does not load the tool. |
| `Program.lean` | library | Reads an ELF into the input of the whole-program lift (`inputOf`), and builds each instruction set's program from it. `decompile` lifts this; `--to lean` modules are checked against it. |
| `Fjimg.lean` | library | The text format of a Flapjack image. |
| `Elf.lean` | library | ELF and symbol-table helpers shared by the tools. |
| `Test/` | built by `lake build Tools` | Unit tests. See [Tests](#tests). |

`NM` is the output of `llvm-nm -S --defined-only ELF`. It supplies function boundaries only,
and those are hints: the kernel re-checks whatever the tools derive from them. Words are read
with riscv-zkvm's ELF parser.

`gen-image`, `infer-contracts` and `frame-sweep` are RISC-V only. Extending them to AArch64 and
x86-64 is part of the roadmap; `decompile` already reads those ELFs through riscv-zkvm's
reader, which is machine-independent.

## `decompile`

The decompiler designed in [`docs/design/Decompiler.md`](../docs/design/Decompiler.md). It lifts
a RISC-V (RV64IM), AArch64 or x86-64 binary to Lprog (`--to lprog`) and on to Pancake
(`--to pancake`). The instruction set is taken from the ELF header.

```
lake exe decompile --to pancake GUEST.elf [OUT.pnk]
lake exe decompile --to lprog   GUEST.elf [OUT.lprog]
lake exe decompile --to lprog --proved GUEST.elf [OUT.lprog]      # RISC-V: the lift the theorems are about
lake exe decompile --to lean --proved [--all] GUEST.elf OUTDIR NAMESPACE # the same, as Lean
lake exe decompile --to lean GUEST.elf OUTDIR NAMESPACE            # the --to lprog program, as Lean
lake exe decompile --to lean --pancake GUEST.elf OUTDIR NAMESPACE  # the --to pancake program, as Lean
lake exe decompile --to lprog|pancake IMAGE.fjimg [OUT]            # a Flapjack image
lake exe decompile --table riscv|aarch64|x86-64 [KINDS]            # the instruction table of a LIMITS.md
lake exe decompile --kinds riscv|aarch64|x86-64 INSTRUCTIONS       # write a KINDS file from a run's instructions
lake exe decompile --listing GUEST.elf                             # x86-64: what the decoder reads
```

**What is proved.** Only the `--proved` RISC-V lift (`liftProg`) has a theorem relating it to
the machine. Nothing else on the way to Pancake is proved; it is tested by running, in
[`scripts/decompile-check`](../scripts/decompile-check/README.md), which recompiles the output
with Flapjack and compares the behaviour of the two binaries.

**Coverage.** What each instruction set's lift does not handle is listed, under the same
headings, in [`RiscV/LIMITS.md`](../MachineChecked/RiscV/LIMITS.md),
[`ARM/LIMITS.md`](../MachineChecked/ARM/LIMITS.md) and
[`X86/LIMITS.md`](../MachineChecked/X86/LIMITS.md). Each includes a table, generated by
`--table`, of the instructions that are lifted and of those the tests run.

### From an ELF

The ELF must not be stripped: its text symbols are the functions. For the build settings that
decide what the proved lift takes from a Rust program, see
[`docs/RustBuilds.md`](../docs/RustBuilds.md). The pipeline is:

1. **Lift 1**, the lift of linked programs (`lprog/Lprog/Linked.lean`), with each instruction
   set's lift of one instruction:
   - RISC-V: `MachineChecked/RiscV/Lift/Whole.lean` (all of RV64IM, far calls, calls that link
     through `t0`);
   - AArch64: `MachineChecked/ARM/Lift/Lift.lean` (integer instructions; flags as registers);
   - x86-64: `MachineChecked/X86/Lift/Lift.lean` (integer instructions, decoded from bytes by
     `X86/Lift/Instr.lean`; return address on the stack).

   Jump tables, indirect calls and tail calls are handled in the shared code.
2. For AArch64 and x86-64, flag writes that nothing reads are dropped (`lprog/Lprog/Dead.lean`).
3. **Lift 2** (`MachineChecked/Logical/Lift.lean`): one Pancake function per function, with
   `if` and `while` where the control flow is structured.
4. **The environment** (`MachineChecked/Logical/Guest.lean`): the program's memory at its own
   addresses, and each system call as an FFI call. An RV64 ELF is treated as an SP1 guest
   (`RiscV/Sp1/`, `@ecall(t0, a0, a1, a2)`); an AArch64 or x86-64 ELF as a program without an
   operating system (`ARM/Bare.lean`, `X86/Bare.lean`, `@syscall(number, a, b, c)`).
5. **The printer** (`pancake/Pancake/Print.lean`).

The Pancake output starts with comments giving the number of functions and how many of them
are an unstructured loop over their blocks, which Pancake function is which symbol, and each
place the program may give up (`l_trap(n)`) with the reason.

**What it refuses.** These inputs are errors: not an ELF, 32-bit, another instruction set,
compressed RISC-V instructions, relocatable or position-independent files, stripped files.
Inside an accepted file, anything the lift does not cover becomes an `l_trap(n)`, where the
Pancake program stops: a word that is not an instruction, a jump out of a function that is
not a call, a computed jump to an address not found in the program, a return to an address
other than the call's. So the output either behaves like the binary or reports where it
stopped.

**What it does not recover.** Registers are global variables, the stack is memory, and nothing
has a type or a name. The output is about as long as the disassembly.

**`--proved`.** `--to lprog --proved` uses `liftProg`, the lift that
`RiscV/Lift/Equiv.lean` proves equivalent to the machine for an observer. It covers less: an
uncovered instruction becomes `abort`, and a function containing a word riscv-zkvm does not
decode is left out, with the instruction, address and reason in a comment. This includes the
nine RV64IM 32-bit operations riscv-zkvm's machine does not run (`addw`, `sllw`, `sraw`,
`sraiw`, `mulw`, `divw`, `divuw`, `remw`, `remuw`), which clang emits for `int` arithmetic. The
one word it takes without decoding it is `unimp`, the illegal instruction compilers write for a
trap: it becomes `trap`, where the machine has no step and the Lprog program traps.

In both lifts the Lprog text is parsed back and compared with the program before it is
written. `Lprog.parse_print` proves the round trip from tokens; this check covers the step
from text.

### As Lean

`decompile --to lean --proved GUEST.elf OUTDIR NS` writes the `--proved` lift as Lean modules
(`ToLean.lean`), as a starting point for proofs about the program:

| module | contents |
| --- | --- |
| `OUTDIR/NS/Words.lean` | Each function's words, and `check_elf_words words "GUEST.elf"`, which reads the ELF when the module is built and adds `words_eq_elf` (the words equal the ELF's) for the kernel to check. `fns` is the functions the words decode to. |
| `OUTDIR/NS/F<i>.lean` | The `i`th function's lift as a term `f<i>`, and `f<i>_eq : (liftProg fns)[i]? = some f<i>`. The kernel checks the name, address and stack bound (`f<i>_head`) and the body in parts of 128 instructions (`f<i>_parts`) by evaluation (`kernel_eq`); `getElem?_eq_of_chunks` combines them. No kernel limit needs raising. |
| `OUTDIR/NS.lean` | Imports everything, and lists each function index with its symbol and address, and each symbol of code left out with the reason. Proofs name functions by index. |

A function left out is not in `fns`, so nothing proved is about it. What is left out is every
symbol of code whose code is not a function of `fns`: a function the lift does not take, and a
symbol no function holds (`Symbols.lost` in `Elf.lean`). The root module lists these, and,
apart, the other names of code that a function of `fns` holds (a second name of one, a label
inside one), which leave nothing out. With `--all`, `decompile` writes nothing and fails if
anything is left out, for a build that must cover all of its code.

The kernel checks that each term is the lift of `fns`. How the term was produced is not
trusted. What remains trusted:

- **The words literal is the ELF's.** The kernel cannot read files, so `check_elf_words` reads
  the ELF at build time with the tool's own reader (`Elf.lean`'s `symbols`, and
  `ElfWords.lean`'s `functions` and `wordsOf`). The path is written as given on the command line and resolved
  from where the module is built, so give it relative to that directory (the repository root,
  for `lake build`). Lake does not track the ELF: if it
  changes, rebuild the words module by hand.
- **The modules are as the tool wrote them.** Check that `Words.lean` defines `fns` from
  `words` and calls `check_elf_words`, and run `#print axioms NS.f<i>_eq`. Symbol names appear
  only in comments, escaped (`commentSafe`).

A misread word cannot produce a false theorem about the binary: `Equiv.lean`'s
`equivalent_of_entry` takes the code at each function's address (`CodeAt`) as a hypothesis,
so a proof about the machine must show the machine holds the words `fns` was built from.

**Namespace.** `NS` is one or more `.`-separated components, each an ASCII upper-case letter
followed by ASCII letters, digits and `_`. It is also a module path under `OUTDIR`: `A.B` is
written as `OUTDIR/A/B.lean` and `OUTDIR/A/B/`. With `OUTDIR` a library's source root, the
modules become part of that library (`Examples/build.sh` uses `OUTDIR` `.` and `NS` `Examples.Arith.RiscV.Image`, and so on). The
target directory must not already exist. The modules are `noncomputable` (the code generator
cannot handle terms this large) and require this repository's root package.

| binary | functions | instructions | Lean written | build of all modules, 8 jobs |
| --- | --- | --- | --- | --- |
| `experiments/leanvm/out/blake2s.elf` | 6 | 702 | 148 KB | 8 s CPU |
| `experiments/zip-2005/out/baseline.elf` | 304 | 41,631 | 8.3 MB | 74 s wall (495 s CPU) on an Apple M3 Max, measured when the parts were checked by `decide`; with `kernel_eq` the longest function takes 11 s (16 s before) |

The two binaries are local builds (`experiments/` is not committed): zip-2005's guest, and the
leanVM guest of [`Examples/LeanVM`](../Examples/LeanVM/README.md).

A one-bit change to a word or a term fails: the words module does not build, or the kernel
rejects the function's statement. `Test/ToLean.lean` checks the latter on a small program.
[`scripts/lean-emit`](../scripts/lean-emit/README.md) builds and times the modules.

#### The other routes: the lift of whole programs, and Pancake

`decompile --to lean GUEST.elf OUTDIR NS` writes the program `--to lprog` gives (RISC-V,
AArch64 or x86-64); `--to lean --pancake` writes the program `--to pancake` gives. Neither lift
is proved. The terms are checked against the lift as for `--proved`:

| module | contents |
| --- | --- |
| `OUTDIR/NS/Code.lean` | The lift's input as `Program.lean` reads it from the ELF (each function's name, address, bytes and possible computed-jump targets; the entry; the memory), and `check_elf_input`, which reads the ELF at build time and adds `code_eq_elf`, `entry_eq_elf` and `memory_eq_elf`. `program` is built from that input by the ELF's own instruction set (`riscvProgram`, `armProgram`, `x86Program`), the same definitions the tool used. |
| `OUTDIR/NS/F<i>.lean` | The `i`th function of `program.lift`, and `f<i>_eq`, checked by `decide +kernel`. |
| `OUTDIR/NS/Pancake.lean` | With `--pancake`, instead of the `F<i>`: the declarations of `program.toPancake` as terms of Flapjack's syntax, and one theorem `pancake_eq : program.toPancake = .ok (decls, notes)` by `kernel_eq` (Flapjack's syntax has no decidable equality). |

What remains trusted is the same in kind: that `check_elf_input` and its reader (`inputOf`,
including its heuristics for computed-jump targets) read the ELF correctly, and that the modules
are as written (check that `Code.lean` calls `check_elf_input`, and `#print axioms`). `program`
is not written out: `check_elf_input` defines it from the ELF's own machine, so a module cannot
lift the code as another instruction set. These terms say only what the lift computes; there is
no theorem relating these lifts to the machine.

**Large functions do not finish.** Here the kernel re-evaluates the whole-program lift (label
maps, and for AArch64 and x86-64 `dropDead`). The lifts use `Std.TreeMap`, which the kernel can
reduce, rather than `Std.HashMap` (the output is the same, byte for byte, on every test binary). The kernel represents arrays as lists, so cost grows much
faster than function size:

| program | route | result |
| --- | --- | --- |
| blake2s (RISC-V) | `--to lean` | input checked; 8 of 9 functions, the largest (38 KB of terms) in 30 s; the ninth (114 KB) unfinished after 15 min |
| `k_iter` (bare AArch64) | `--to lean` | input in 6 s; 29 of 35 functions, up to 14 min each (21 KB); the six largest (30 to 125 KB) unfinished after 40 min |
| blake2s (RISC-V) | `--to lean --pancake` | terms elaborate in 2 s; `pancake_eq` unfinished after 30 min (mostly memory) |
| two-instruction functions, each ISA | `Test/ToLean.lean` | each lift, a changed AArch64 term refuted, lift 2 and its names by `kernel_eq`, false equations refused; seconds, in CI |
| the small ELF of `Test/Elf.lean` (RISC-V, 3 functions) | all three routes, `scripts/to-lean-check/check.sh` | every module written and built; a changed word, byte or note refused; the function list of an unsized last `_start`, of a label and of a function past `.text`; with `unimp` in `_start`, every function taken, also under `--all`; with `addw` there, the function named as left out and `--all` refused; `--all` taking a label that is only a name; a function's module imports neither `Tools.ToLean` nor `Lean`; in CI |

The fix planned is to check a certificate the tool writes (labels, live flags) instead of
re-evaluating the lift ([`Packages.md`](../docs/design/Packages.md) step 3a).

### From a Flapjack image

`decompile --to pancake IMAGE.fjimg` takes a Flapjack binary in flapjack-flip's text format. It
uses lift 1 for code without functions (`RiscV/Lift/Flat.lean`) in the Flapjack image layout
(`RiscV/Flapjack/`), then lift 2. Flapjack's output has no function boundaries and returns
through computed jumps, so the whole image becomes one function that loops over its blocks.
The decompiled image gets half the original heap and half the stack.

## Tests

`Tools/Test/` holds unit tests as `#guard`s and theorems evaluated at build time, so
`lake build Tools` (and CI) fails if one does not hold. Expected values come from each
instruction set's manual, worked out by hand, not from the code under test. To run one file:
`lake env lean Tools/Test/X86.lean` (no output means it passed).

| file | `#guard`s | theorems and examples | what |
| --- | --- | --- | --- |
| `Run.lean` | | | Helper: runs one instruction's lift on concrete registers and byte memory, and reports how it ends (next instruction, branch target, give up, `wrong`, or leaving the function). |
| `RiscV.lean` | 222 | 1 | `decodeWord` and the whole-program RV64IM lift: each `*w` instruction, division by zero and overflow, loads and stores of each width, `x0`, branches, calls and far calls (`auipc` + `jalr`), computed jumps, the `--proved` lift's call candidates (`jalrCands`), and a function of the `--proved` lift from its own code and a table of its callees (`Fn.callTargets`, `getElem?_liftProg_of_callTargets`). |
| `Arm.lean` | 342 | | The AArch64 lift from instruction words: flags through the conditions that read them, logical immediates, bitfields, conditional select and compare, loads and stores with writeback, branches. |
| `X86.lean` | 392 | | The x86-64 decoder and lift from bytes: prefixes and addressing forms, flags at every size, partial register writes, shifts, division, the stack, string instructions with `rep`. |
| `Dead.lean` | 45 | | Dropping unread flag writes: what is dropped and kept, and that a body runs the same before and after. |
| `Text.lean` | 55 | | The Lprog text format: each instruction kind parsed back from its text; malformed text rejected. |
| `Elf.lean` | 67 | | The ELF reader on a small hand-made file and on truncated and malformed ones: each gives an error, none crashes. The function list: an unsized `_start` that is the last symbol, aliases and local labels (a name where a function holds them, left out where none does), a label and a function past `.text`. |
| `Structure.lean` | 6 | | Control-flow structuring on small graphs: a switch is never a two-way choice or an exit. |
| `ToLean.lean` | 29 | 10 | `decompile --to lean`: a body checked in parts, a function's theorem from its parts, a changed term refuted by the kernel, symbol names escaped in comments, accepted namespaces; the other routes on one small function per instruction set. |
| `Lsym.lean` | 6, and one `#guard_msgs` | 19 | `lsym` (`lprog/Lprog/Tactic.lean`) on small RISC-V functions: a branch, two paths, a return; a call through the callee's specification and through a contract (`Isa.Contract`); the address normal form; the names of the hypotheses it adds. |
| `LsymX86.lean` | | 5 | `lsym` on x86-64: two functions lifted from bytes (checked against the lift), a call that pushes and pops its return address, proved through the callee's contract over a model of x86-64 memory. |
