# Limits of `decompile` on AArch64

What `decompile --to pancake` does and does not do with an AArch64 program. Each instruction
set's `LIMITS.md` has the same sections in the same order: [RISC-V](../RiscV/LIMITS.md),
[x86-64](../X86/LIMITS.md).

The tool is tested, not proved; see [How far it is tested](#how-far-it-is-tested).

## What it accepts

- **A statically linked, little-endian ELF64 executable with its symbol table.** Functions
  are its sized text symbols, one per address, and its global text symbols without a size,
  each up to the next symbol or the end of its section; every other symbol of code is reported
  with the reason, but for an untyped label without a size outside its section, which is no
  code. Stripped files, relocatable files and position-independent executables are refused.
- **The integer instructions of AArch64**, as arm64-semantics decodes them. No SIMD or
  floating point: build for a target without them (`aarch64-unknown-none-softfloat`), or the
  program gives up at the first such instruction it runs.
- **A program without an operating system.** A system call is `svc #0` with the number in
  `x8`, arguments in `x0` to `x2`, and the result in `x0`.

## Where it gives up

It never knowingly produces a wrong result. It either refuses with a message, or produces a
program that reports where it stopped.

**The tool refuses the file** (message, exit status 1) if:

- it is not an ELF, not 64-bit, not little-endian, or not a statically linked executable;
- it has no function symbols;
- the ELF entry point is not the start of a function.

A function whose symbol is not 4-byte aligned, or not inside an executable segment, is left
out and named in a comment in the output. A call to it gives up.

**The output gives up at run time.** Every point where the lifted program can stop is
numbered and listed in comments at the top of the output (`// trap 12: f3, after label 40:
...`). A program that reaches one calls `@trap(12, 0, 0, 0)` and stops; the runner reports
`gave up (trap 12)`. These points are:

- **an instruction the lift does not cover** (see the table);
- **a computed jump to an address that is not one of its candidates.** The candidates are the
  addresses inside the function that the tool finds held as values: the 8-byte words of its
  data, and, for a table of offsets, the address formed by an `adr` in the four instructions
  before the `br` plus each 4-byte word of the data. If the tool does not find a jump table,
  the program gives up at the jump;
- **an indirect call to an address that is not a function entry**;
- **a call that returns with a different return address, or a return or tail call with the
  stack pointer not where it was on entry.** So `longjmp`, unwinding, coroutines, and anything
  else that leaves a function other than by returning, give up;
- **control leaving a function other than by a call, tail call or return**: a branch into
  the middle of another function, or running off the end.

## What it assumes without checking

- **The symbols are correct.** A function is the bytes its symbol covers. Code not covered by
  a sized symbol is not lifted, and a jump there gives up.
- **The code does not change.** The output is the code as it is in the file. A program that
  writes or generates code runs the old code: the bytes are also in the output's memory as
  data, and a write changes only that data.
- **One thread, no interrupts.**
- **The environment is that of `scripts/decompile-check`**: four system calls, numbered as in
  SP1: `HALT`, `WRITE`, `HINT_LEN`, `HINT_READ` (`rust/src/bare.rs`).
- **The output runs on the runner's machine** (`scripts/decompile-check/sp1run.py`): the
  Pancake program's heap is the original's whole address space up to 2^40, so it reads and
  writes the original's addresses. No such machine is defined in Lean yet.

## Where the output differs from the processor

- **Memory does not fault.** The whole address space below 2^40 is readable and writable. A
  load or store that would fault on the processor (unmapped or read-only page) reads zero or
  writes, and the program continues.
- **Loads and stores need not be aligned**, and Pancake does not define a word access at an
  address that is not a multiple of eight. The output is tested on a machine that allows it;
  on one that does not, it would fail where the original does not.
- **Stack-pointer alignment is not checked**, although the processor can be configured to.
- **Division by zero gives zero**, as on the processor.
- **Only user-level state**: no system registers, no exception levels. `svc` is the only
  exception.
- **Timing.** The output takes 10.4 times as many steps as the original on the tests, and
  nothing about the cost of an operation is preserved: constant-time code is not constant-time
  afterwards.
- **Only functions and control flow are recovered.** Registers are global variables, the
  stack is memory, and nothing has a name or a type.

## How far it is tested

Each program is decompiled, the Pancake is compiled with Flapjack, both are run, and every
system call and the final status are compared on five inputs. The method and its blind spots
are in [`scripts/decompile-check/README.md`](../../scripts/decompile-check/README.md). As of
2026-11-16:

| | |
| --- | --- |
| programs | 263 programs in Rust for `aarch64-unknown-none-softfloat` (rustc 1.98, `opt-level = 3`): 36 written by hand, 227 generated. The same sources as the SP1 guests |
| pass | **263 / 263** |
| reference for what the original does | Unicorn 2.1 (QEMU's emulation of the processor) |
| instructions of the programs that some input runs | 32% |
| kinds of instruction lifted, and run | 91 lifted, all 91 run |
| one-bit changes to the output | of 71 that some input reaches, 38 change what the test sees (on 262 of the programs) |
| steps, output over original | 10.4 |

All programs come from one compiler at one setting. Nine of the instruction kinds are run
only by `scripts/decompile-check/rust/src/bin/k_arm.rs`, which writes them by hand.

The 33 one-bit changes that are reached but not seen were each inspected. About a third
change a callee-saved register as it is saved or restored. Others change the difference a
comparison computes for its flags (2 of 10 such changes are seen), or a value that nothing
visible to the test reads afterwards (a system call's result, or a register overwritten
before use). Of 40 reached changes to a general register, 24 are seen. That none of the 33
can be seen was not proved.

## What is proved

Nothing. The instructions and their decoder are arm64-semantics' (`Arm64.lean`), but the lift
(`Lift/Lift.lean`) is not proved against `Arm64.Step`: each instruction's behaviour is written
again here and tested against Unicorn, which is QEMU's emulation, not arm64-semantics.
