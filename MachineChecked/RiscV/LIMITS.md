# Limits of `decompile` on RISC-V

What `decompile --to pancake` does and does not do with a program for RISC-V. The same
headings, in the same order, are in the `LIMITS.md` of each instruction set:
[AArch64](../ARM/LIMITS.md), [x86-64](../X86/LIMITS.md).

The tool is tested, not proved. What the tests show is under "How far it is tested".

## What it takes

- **A statically linked ELF64 executable, little-endian, with its symbol table.** The
  functions are its sized text symbols. A stripped file, a relocatable file and a
  position-independent executable are refused.
- **RV64IM**, without compressed instructions: an ELF that says it uses them is refused.
- **An SP1 guest** (SP1 6.10.0): its system calls are `ecall` with the number in `t0`. A
  Flapjack image (`.fjimg`) is also taken, by another lift (`Lift/Flat.lean`), as one
  function.

## Where it gives up

Never by a wrong result that it knows of: by a message, or by a program that says where it
stopped.

**The tool refuses the file**, with a message and exit status 1:

- not an ELF, not 64-bit, not little-endian, not RISC-V, not a statically linked executable;
- compressed instructions (RVC);
- no function symbols;
- the entry of the ELF is not the start of a function.

A function whose symbol is not at a multiple of four, or not inside an executable segment,
is left out and named in a comment of the output; a call of it gives up.

**The output gives up as it runs.** Every place where the lifted program can stop is
numbered, and listed in comments at the top of the output (`// trap 12: f3, after label 40:
...`). A program that reaches one calls `@trap(12, 0, 0, 0)` and goes no further; the runner
reports `gave up (trap 12)`. The places are:

- **an instruction the lift does not cover** (the table above);
- **a computed jump to an address that is none of its candidates.** The candidates are the
  addresses inside the function that the tool finds held as values:
  the eight-byte words of its data, and the addresses its code forms with `auipc` or
  `lui` and an `addi` within 24 instructions.
  A table the tool does not find makes the program give up at the jump;
- **an indirect call of an address that is not the entry of a function**;
- **a call that came back with another return address, or a return or tail call with the
  stack pointer not where the function was entered.** So `longjmp`, unwinding, coroutines
  and anything else that leaves a function other than by returning give up;
- **control that leaves a function other than by a call, a tail call or a return**: a
  branch into the middle of another function, or running off the end.

## What it assumes and does not check

- **The symbols are right.** A function is the bytes its symbol covers. Code that no sized
  symbol covers is not lifted, and a jump there gives up.
- **The code does not change.** The output is the code as it is in the file. A program that
  writes its own code, or makes code as it runs, runs the old code: the bytes are also in
  the output's memory as data, and a write to them changes only that.
- **One thread, no interrupts.**
- **The environment is the one of `scripts/decompile-check`.**
  SP1's system calls `HALT`, `WRITE`, `COMMIT`, `COMMIT_DEFERRED_PROOFS`, `HINT_LEN`
  and `HINT_READ`. A program that uses another (a precompile) is decompiled, and the
  runner refuses the call.
- **The machine the output runs on is the runner's** (`scripts/decompile-check/sp1run.py`):
  the Pancake program's heap is the original's whole address space up to 2^40, so it reads
  and writes the original's addresses. No such machine is defined in Lean yet.

## Where the output differs from the processor

- **Memory does not fault.** All of the address space below 2^40 can be read and written. A
  load or store that would fault on the processor (no page there, or a read-only one) reads
  zero or writes, and the program goes on.
- **A load or store must be aligned**, in the original as SP1 has it and in the output:
  the runner fails both on one that is not.
- **The limits SP1 puts on addresses are not modelled.**
- **Time.** The output takes 7.0 times the steps of the original on the tests, and
  nothing about how long an operation takes is kept: a program that is constant-time is not
  so afterwards.
- **Nothing is recovered but functions and control flow.** Registers are global variables,
  the stack is memory, nothing has a name or a type.

## How far it is tested

By decompiling, compiling the Pancake with Flapjack, running both, and comparing every
system call and the final status on five inputs (`scripts/decompile-check/README.md`, where
the method and what it does not show are written out). On 2026-11-16:

| | |
| --- | --- |
| programs | 267 SP1 guests in Rust (SP1 6.10.0, rustc 1.93, `opt-level = 3`): 41 written by hand, 226 generated. And 612 Flapjack images, on the other lift |
| pass | **267 / 267 guests, 612 / 612 images** |
| reference for what the original does | SP1's own executor, which agrees with the runner here on all 267: public values, exit code, number of instructions. For the images, flapjack-flip's machine |
| instructions of the programs that some input runs | 48% |
| kinds of instruction lifted, and run | 64 lifted, 63 of them run (`FENCE` is not) |
| one-bit changes to the output | of 124 that some input reaches, 102 change what the test sees (measured 2026-11-15, on 265 of the guests) |
| steps, output over original | 7.0 |

Every guest is from one compiler at one setting. Hand-written assembly is tested only as far as
`scripts/decompile-check/rust/src/bin/k_asm_*.rs` write it: every instruction of RV64IM with
edge-case operands, a jump table in code, a call through `t0`, `jalr` with one register for
target and link.

## What is proved

Of this route, nothing. `decompile --to lprog --proved` is another lift (`liftProg`), of the
functions that follow the calling convention, and that one is proved equivalent to the
machine (`Lift/Equiv.lean`). The lift of whole programs (`Lift/Whole.lean`) and lift 2
(`../Logical/Lift.lean`) are not. The 32-bit operations riscv-zkvm's instruction type lacks
are stated here (`Lift/Decode.lean`) and tested against SP1's executor.
