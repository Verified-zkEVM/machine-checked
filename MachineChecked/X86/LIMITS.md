# Limits of `decompile` on x86-64

What `decompile --to pancake` does and does not do with an x86-64 program. Each instruction
set's `LIMITS.md` has the same sections in the same order: [RISC-V](../RiscV/LIMITS.md),
[AArch64](../ARM/LIMITS.md).

The tool is tested, not proved; see [How far it is tested](#how-far-it-is-tested).

## What it accepts

- **A statically linked, little-endian ELF64 executable with its symbol table.** Functions
  are its sized text symbols. Stripped files, relocatable files and position-independent
  executables are refused.
- **The integer instructions of x86-64 in 64-bit mode**, as this repository's decoder reads
  them (`Lift/Instr.lean`); Kraken's model has no decoder. No x87, MMX, SSE or AVX: build for
  a target without them (`x86_64-unknown-none`), or the program gives up at the first such
  instruction it runs.
- **A program without an operating system.** A system call is `syscall` with the number in
  `rax`, arguments in `rdi`, `rsi` and `rdx`, and the result in `rax`.

## Instructions

The table is generated by `decompile --table x86-64` from the lift itself, together with the
instruction kinds the tests run (`scripts/decompile-check/run/x86-64.txt`). `check.py limits`
fails if it differs from the generated table. A kind counts as lifted if lifting one
instruction of that kind produces no `Labort`.

An instruction is the same kind at every operand size, unless the table says otherwise.

The last kind is everything the decoder does not read:

- the prefixes `lock`, `F2`, `67`, `fs` and `gs`;
- a REX prefix that is not the last prefix (the processor ignores it);
- VEX and EVEX; x87, MMX and SSE;
- `cmpxchg`, `xadd`, `cmps`, `scas`, `lods`, `rcl`, `rcr`, `enter`, `ret` with a count,
  `pushf`, `popf`, `lahf`, `sahf`, `xlat`, `cpuid`, `rdtsc`, one-byte `xchg`, `movsxd` to 32
  bits, 16-bit `push` and `pop`, and the bit instructions on memory with a register index;
- `endbr64`, so code built for CET (with one at the start of each function) is not lifted at
  all;
- system instructions.

A function is decoded from its start, so once the decoder meets bytes it cannot read, the
rest of the function is not lifted either.

## Where it gives up

It never knowingly produces a wrong result. It either refuses with a message, or produces a
program that reports where it stopped.

**The tool refuses the file** (message, exit status 1) if:

- it is not an ELF, not 64-bit, not little-endian, or not a statically linked executable;
- it has no function symbols;
- the ELF entry point is not the start of a function.

**The output gives up at run time.** Every point where the lifted program can stop is
numbered and listed in comments at the top of the output (`// trap 12: f3, after label 40:
...`). A program that reaches one calls `@trap(12, 0, 0, 0)` and stops; the runner reports
`gave up (trap 12)`. These points are:

- **an instruction the lift does not cover** (see the table);
- **a computed jump to an address that is not one of its candidates.** The candidates are the
  addresses inside the function that the tool finds held as values: the 8-byte words of its
  data, the addresses its code names (`lea`, a constant), and, for a table of offsets, an
  address named in the eight instructions before the `jmp` plus each 4-byte word of the data.
  If the tool does not find a jump table, the program gives up at the jump;
- **an indirect call to an address that is not a function entry**;
- **a call that returns with a different return address, or a return or tail call with the
  stack pointer not where it was on entry.** So `longjmp`, unwinding, coroutines, and anything
  else that leaves a function other than by returning, give up;
- **control leaving a function other than by a call, tail call or return**: a branch into
  the middle of another function, or running off the end;
- **a division that faults on the processor**: by zero, or with a quotient that does not fit;
- **a 64-bit `idiv` whose dividend does not fit in `rax`**, that is, where `rdx` is not the
  sign extension of `rax`. After `cqo`, as compilers emit it, it always is. The table lists
  `idiv` as lifted because its lift has no `Labort`; this case gives up at run time. The
  unsigned `div` uses all 128 bits of `rdx:rax`.

## What it assumes without checking

- **The symbols are correct.** A function is the bytes its symbol covers. Code not covered by
  a sized symbol is not lifted, and a jump there gives up.
- **The code does not change.** The output is the code as it is in the file. A program that
  writes or generates code runs the old code: the bytes are also in the output's memory as
  data, and a write changes only that data.
- **One thread, no interrupts.**
- **The environment is that of `scripts/decompile-check`**: four system calls, numbered as in
  SP1: `HALT`, `WRITE`, `HINT_LEN`, `HINT_READ` (`rust/src/bare.rs`).
- **The output runs on the runner's machine** (`scripts/decompile-check/sp1run.py`): the
  Pancake program's heap is the original's whole address space up to 2^40, so it reads and
  writes the original's addresses. No such machine is defined in Lean yet.

## Where the output differs from the processor

- **Memory does not fault.** The whole address space below 2^40 is readable and writable. A
  load or store that would fault on the processor (unmapped or read-only page) reads zero or
  writes, and the program continues.
- **Loads and stores need not be aligned**, and Pancake does not define a word access at an
  address that is not a multiple of eight. The output is tested on a machine that allows it;
  on one that does not, it would fail where the original does not.
- **The auxiliary-carry flag is not kept.** No instruction that reads it is decoded.
- **Flags the processor leaves undefined** (overflow after a shift by more than one; zero,
  sign and parity after a multiplication; all but zero after `bsf` and `bsr`) are left
  unchanged or given the value common processors give. `bsf` and `bsr` of zero leave their
  destination unchanged.
- **`F3 0F BC` and `F3 0F BD` are `tzcnt` and `lzcnt`.** A processor without them runs the
  same bytes as `bsf` and `bsr`.
- **`syscall` does not write `rcx` and `r11`**, unlike the processor.
- **Return addresses are on the stack as in the original**, and the output also keeps one in
  a dedicated register while a call or return passes it (`Lift/Lift.lean`).
- **Timing.** The output takes 15.5 times as many steps as the original on the tests, and
  nothing about the cost of an operation is preserved: constant-time code is not constant-time
  afterwards.
- **Only functions and control flow are recovered.** Registers are global variables, the
  stack is memory, and nothing has a name or a type.

## How far it is tested

Each program is decompiled, the Pancake is compiled with Flapjack, both are run, and every
system call and the final status are compared on five inputs. The method and its blind spots
are in [`scripts/decompile-check/README.md`](../../scripts/decompile-check/README.md). As of
2026-11-16:

| | |
| --- | --- |
| programs | 263 programs in Rust for `x86_64-unknown-none` (rustc 1.98, `opt-level = 3`, `relocation-model=static`): 36 written by hand, 227 generated. The same sources as the SP1 guests |
| pass | **263 / 263** |
| reference for what the original does | Unicorn 2.1 (QEMU's emulation of the processor). The decoder agrees with `llvm-objdump` on all 1,062,210 instructions of the programs: where each starts, and its name |
| instructions of the programs that some input runs | 31% |
| kinds of instruction lifted, and run | 110 lifted, all 110 run |
| one-bit changes to the output | of 99 that some input reaches, 51 change what the test sees |
| steps, output over original | 15.5 |

All programs come from one compiler at one setting. Eleven of the instruction kinds are run
only by `scripts/decompile-check/rust/src/bin/k_x86.rs`, which writes them by hand.

Of 50 reached one-bit changes to a general register, 27 are seen; of 19 to the value an
instruction computes for its flags, 10; of 14 to a flag, 3. Unlike AArch64's, the unseen
changes were not inspected individually.

## What is proved

Nothing, and less is shared with a trusted model than on the other two instruction sets. The
instruction type and decoder are this repository's (`Lift/Instr.lean`), because Kraken's x64
model takes assembly, not bytes, and lacks some instructions compilers emit (`div`, `idiv`,
`bsr`, `tzcnt`, `bt`, `bts`, `cdqe` and its family, `syscall`). The decoder is compared with
LLVM's disassembler on every instruction of the tests, for where each starts and its name
(`scripts/decompile-check/x86dis.py`). The lift is tested against Unicorn. Neither is compared
with Kraken's semantics yet.
