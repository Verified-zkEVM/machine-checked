# Limits of `decompile` on x86-64

What `decompile --to pancake` does and does not do with a program for x86-64. The same
headings, in the same order, are in the `LIMITS.md` of each instruction set:
[RISC-V](../RiscV/LIMITS.md), [AArch64](../ARM/LIMITS.md).

The tool is tested, not proved. What the tests show is under "How far it is tested".

## What it takes

- **A statically linked ELF64 executable, little-endian, with its symbol table.** The
  functions are its sized text symbols. A stripped file, a relocatable file and a
  position-independent executable are refused.
- **The integer instructions of x86-64 in 64-bit mode**, as the decoder here reads them
  (`Lift/Instr.lean`): Kraken's model has no decoder. Nothing of x87, MMX, SSE or AVX: a
  program must be built for a target without them (`x86_64-unknown-none`), or it gives up
  at the first such instruction it runs.
- **A program without an operating system.** A system call is `syscall` with the number in
  `rax`, the arguments in `rdi`, `rsi` and `rdx`, and the result in `rax`.

## Instructions

Generated by `decompile --table x86-64` from the lift itself, with the kinds of instruction
the tests run (`scripts/decompile-check/run/x86-64.txt`); `check.py limits` fails if this is
not the generated table. A kind is lifted if the lift of one instruction of it has no
`Labort`.

An instruction is of the same kind at every operand size, unless the table says otherwise.
What the decoder does not read is one kind, the last: the prefixes `lock`, `F2`, `67`, `fs`
and `gs`; a REX prefix that is not the last prefix (the processor ignores it); VEX and EVEX; x87, MMX and SSE; `cmpxchg`, `xadd`, `cmps`, `scas`, `lods`, `rcl`,
`rcr`, `enter`, `ret` with a count, `pushf`, `popf`, `lahf`, `sahf`, `xlat`, `cpuid`,
`rdtsc`, `xchg` of one byte, `movsxd` to 32 bits, `push` and `pop` of 16 bits, the bit
instructions on memory with a register for the index, `endbr64` (so code built for CET, with
one at the start of each function, is not lifted at all), and the instructions for the
system. A function is read from its start, so after bytes the decoder does not read, the
rest of the function is not lifted either.

## Where it gives up

Never by a wrong result that it knows of: by a message, or by a program that says where it
stopped.

**The tool refuses the file**, with a message and exit status 1:

- not an ELF, not 64-bit, not little-endian, not a statically linked executable;
- no function symbols;
- the entry of the ELF is not the start of a function.

**The output gives up as it runs.** Every place where the lifted program can stop is
numbered, and listed in comments at the top of the output (`// trap 12: f3, after label 40:
...`). A program that reaches one calls `@trap(12, 0, 0, 0)` and goes no further; the runner
reports `gave up (trap 12)`. The places are:

- **an instruction the lift does not cover** (the table above);
- **a computed jump to an address that is none of its candidates.** The candidates are the
  addresses inside the function that the tool finds held as values:
  the eight-byte words of its data, the addresses its code names (`lea`, a constant),
  and, for a table of offsets, an address named in the eight instructions before the `jmp`
  plus each four-byte word of the data.
  A table the tool does not find makes the program give up at the jump;
- **an indirect call of an address that is not the entry of a function**;
- **a call that came back with another return address, or a return or tail call with the
  stack pointer not where the function was entered.** So `longjmp`, unwinding, coroutines
  and anything else that leaves a function other than by returning give up;
- **control that leaves a function other than by a call, a tail call or a return**: a
  branch into the middle of another function, or running off the end;
- **a division that faults on the processor**: by zero, or with a quotient that does not fit;
- **a 64-bit `idiv` whose dividend does not fit in `rax`**: one where `rdx` is not the sign
  of `rax`. After `cqo`, as compilers emit it, it always is. The table says `idiv` is lifted
  because its lift has no `Labort`; this case gives up as it runs. The unsigned `div` takes
  all 128 bits of `rdx:rax`.

## What it assumes and does not check

- **The symbols are right.** A function is the bytes its symbol covers. Code that no sized
  symbol covers is not lifted, and a jump there gives up.
- **The code does not change.** The output is the code as it is in the file. A program that
  writes its own code, or makes code as it runs, runs the old code: the bytes are also in
  the output's memory as data, and a write to them changes only that.
- **One thread, no interrupts.**
- **The environment is the one of `scripts/decompile-check`.**
  Four system calls, numbered as SP1's: `HALT`, `WRITE`, `HINT_LEN`, `HINT_READ`
  (`rust/src/bare.rs`).
- **The machine the output runs on is the runner's** (`scripts/decompile-check/sp1run.py`):
  the Pancake program's heap is the original's whole address space up to 2^40, so it reads
  and writes the original's addresses. No such machine is defined in Lean yet.

## Where the output differs from the processor

- **Memory does not fault.** All of the address space below 2^40 can be read and written. A
  load or store that would fault on the processor (no page there, or a read-only one) reads
  zero or writes, and the program goes on.
- **A load or store need not be aligned**, and Pancake does not say what a word access
  at an address that is not a multiple of eight does. The output is tested on a machine that
  allows it; on one that does not, it would fail where the original does not.
- **The auxiliary-carry flag is not kept.** No instruction that reads it is decoded.
- **A flag the processor leaves undefined** (the overflow flag after a shift by more than
  one; the zero, sign and parity flags after a multiplication; all but the zero flag after
  `bsf` and `bsr`) is left as it was or given the value the usual processors give. `bsf`
  and `bsr` of zero leave their destination as it was.
- **`F3 0F BC` and `F3 0F BD` are `tzcnt` and `lzcnt`.** A processor without them runs the
  same bytes as `bsf` and `bsr`.
- **`syscall` does not write `rcx` and `r11`**, as the processor does.
- **A return address is on the stack as in the original**, and the output also keeps it in
  a register of its own while a call or return passes it (`Lift/Lift.lean`).
- **Time.** The output takes 15.5 times the steps of the original on the tests, and
  nothing about how long an operation takes is kept: a program that is constant-time is not
  so afterwards.
- **Nothing is recovered but functions and control flow.** Registers are global variables,
  the stack is memory, nothing has a name or a type.

## How far it is tested

By decompiling, compiling the Pancake with Flapjack, running both, and comparing every
system call and the final status on five inputs (`scripts/decompile-check/README.md`, where
the method and what it does not show are written out). On 2026-11-16:

| | |
| --- | --- |
| programs | 263 programs in Rust for `x86_64-unknown-none` (rustc 1.98, `opt-level = 3`, `relocation-model=static`): 36 written by hand, 227 generated. The same sources as the SP1 guests |
| pass | **263 / 263** |
| reference for what the original does | Unicorn 2.1 (QEMU's emulation of the processor). The decoder agrees with `llvm-objdump` on all 1,062,210 instructions of the programs: where each starts, and its name |
| instructions of the programs that some input runs | 31% |
| kinds of instruction lifted, and run | 110 lifted, all 110 run |
| one-bit changes to the output | of 99 that some input reaches, 51 change what the test sees |
| steps, output over original | 15.5 |

Every program is from one compiler at one setting, and eleven of the kinds of instruction
are run only by `scripts/decompile-check/rust/src/bin/k_x86.rs`, which writes them by hand.
Of 50 reached one-bit changes to a general register, 27 are seen; of 19 to the result an
instruction computes for its flags, 10; of 14 to a flag, 3. The ones not seen were not read
one by one, as AArch64's were.

## What is proved

Nothing, and less is shared with a trusted model than for the other two: the instruction
type and the decoder are this repository's (`Lift/Instr.lean`), because Kraken's x64 model
takes assembly, not bytes, and lacks some instructions compilers emit (`div`, `idiv`, `bsr`,
`tzcnt`, `bt`, `bts`, `cdqe` and its family, `syscall`). The decoder is compared with
LLVM's disassembler on every instruction of the tests, for where each starts and its name
(`scripts/decompile-check/x86dis.py`); the lift is tested against Unicorn. Neither is
compared with Kraken's semantics yet.
